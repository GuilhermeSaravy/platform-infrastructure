# Architecture and ownership

Northstar Commerce has platform-engineering, commerce-backend and commerce-frontend teams, catalog/orders projects and dev/prod environments. Existing Entra security groups belong to the separate conceptual `organization-identity` repository. Their runtime object-ID mapping is never committed. The same groups have different environment permissions. Contributor grants management access and can modify workloads to exercise their identities: dev developers are trusted. Production developers receive Reader. Blob data roles are separate.

Organization defaults, naming and access semantics are centralized. Projects declare needs and explicit Azure options. Declarations use the JSON subset of YAML so the checker needs no Python packages. Editable defaults are West Europe, B1 Linux, StorageV2 Standard LRS, TLS1.2, dev 10.40.0.0/16 and prod 10.50.0.0/16. Current quota, policy and regional availability must be checked manually later.

Each environment has one platform-owned network state: `vnet-dev` in `rg-platform-network-dev`, and `vnet-prod` in `rg-platform-network-prod`. There is no dev/prod peering or cross-environment grant. Platform owns addressing, subnets, rules, routing and Private DNS. Project network_slot allocates a dedicated /26 delegated to Microsoft.Web/serverFarms. Private Endpoints occupy a separate shared /24; operators have a reserved /24. The platform discovers `projects/*/project.yaml`; there is no central project list.

Runtime subnets allow HTTPS to Private Endpoints and platform DNS and deny other VNet traffic. Endpoint ingress permits runtime/operator HTTPS and denies other VNet traffic. Network reachability does not grant container authorization. App Service public Internet egress for platform/image dependencies remains on default routing; this foundation does not implement an egress firewall. Private app and storage ingress have public access disabled. Endpoint and integration subnets differ.

Each project/environment resources state owns its resource group, plans/runtimes, workload UAMIs, storage and Private Endpoints. Catalog and orders each have an api identity; orders owns exports and restricted containers. Separate access states own human roles and destination-controlled workload grants. Orders/dev resolves catalog/dev/api through its named Azure identity contract and assigns Storage Blob Data Reader at the destination exports container's ARM scope. No source Terraform state is exposed. Apply both resource units before access; revoke grants before destroying workloads. Outputs have contract_version=1.

Shared resources have one state owner. Project units discover shared resources through narrow ARM data sources. For project removal, destroy access and project resources while its declaration still exists; only then remove the declaration and apply the network state to remove its unused subnet. Shared VNet/DNS remain. Never recycle a network slot until old integration and endpoints are gone.

Bootstrap uses an already authenticated local operator to create state storage, deployment UAMI and GitHub federated credential. The identity cannot create itself before authentication. Local bootstrap state is retained securely or explicitly migrated to a dedicated backend key. Remote state uses Blob lease locking, Azure AD, HTTPS, no shared keys, versioning and restricted data roles. The public state endpoint is an explicit exception for GitHub-hosted runners. State and saved plans are confidential even when Terraform outputs are sensitive.

Governance defines custom policies and assignments scoped to owned resource groups, excluding bootstrap. Apply it after the resource groups exist. This initial provisioning gap is explicit; a stricter landing zone could preassign policies from a separate privileged repository. Governance enforces regions, tags and selected app/storage security restrictions after assignment and propagation.

Azure resource RBAC does not authorize arbitrary application HTTP endpoints. The private demo exposes fixed dev probes for a private operator; probes are disabled on orders and in prod. It is not an application authentication pattern. Human acceptance execution requires an existing private-connected host/VPN and DNS forwarding; GitHub-hosted runners use management APIs and the state endpoint only.

Reusable future concepts include ownership, profiles, environments, destination-owned grants and onboarding validation. AWS identity, networking, policies, backend and service schemas would need their own implementation and tests. No unchanged configuration compatibility is promised. Kubernetes, portals/frontends, AI, Databricks, third-party monitoring and multi-cloud code are outside scope.
